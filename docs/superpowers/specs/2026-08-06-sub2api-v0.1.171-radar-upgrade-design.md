# Sub2API v0.1.171 Radar Upgrade Design

**Status:** User-approved design

**Date:** 2026-08-06

## Goal

Upgrade the embedded Sub2API Radar platform from
`0.1.164-radar-v10.20260806` to a dedicated `0.1.171-radar-v11`
candidate. The candidate incorporates official Sub2API `v0.1.171` while
preserving the current Radar control plane, managed Workers, embedded
console pages, data, migration history, and rollback asset.

## Sources

- Official release: <https://github.com/Wei-Shaw/sub2api/releases/tag/v0.1.171>
- Official tagged commit: <https://github.com/Wei-Shaw/sub2api/tree/f0e7a9c7a23a7d02fb159b62fa809621eb0475a6>

## Baseline

- The offshore control plane image is
  `sub2api/radar-control-plane:radar-v10-candidate-20260806T102417Z`.
- The running binary reports `0.1.164-radar-v10.20260806`.
- The source branch is `codex/radar-v10-platform-integration` in the
  isolated `.worktrees/radar-v10-release` worktree.
- The worktree contains uncommitted Radar changes. A checksum manifest and
  patch artifact preserve them before any merge.
- `radar.weihub.cloud` stays decommissioned with HTTP 410. Radar remains
  inside the existing Sub2API console.
- Radar and official `v0.1.171` share 38 changed paths, including wiring,
  gateway accounting, administrative routes, service wiring, router code,
  and one migration path.

## Scope

This release includes official `v0.1.171` functionality and security fixes,
Radar control-plane compatibility, fixed-digest Radar Workers, embedded
Radar and model-health pages, disposable database rehearsal, offshore trial,
and production promotion evidence.

This release excludes a standalone Radar domain, new benchmark suites,
pricing policy changes, Worker protocol feature additions, and weakened
CAPTCHA controls.

## Architecture

### Source Integration

Create `codex/radar-v11-v0.1.171` from the Radar v10 release head after
preserving the dirty worktree. Merge the official tagged commit with a
three-way merge so Git has the current shared base for conflict resolution.

Resolve conflicts by ownership:

| Area | Rule |
| --- | --- |
| CAPTCHA, Codex identity, billing, refunds, upstream transport | Preserve official `v0.1.171` semantics and reconnect Radar extension points. |
| Radar repositories, handlers, services, Worker routes, evidence flow | Preserve Radar behavior and adapt it to official interfaces. |
| Wire providers and generated wiring | Combine provider sets, regenerate wiring, and construct the server in tests. |
| Console router and translations | Preserve in-app Radar navigation and merge official router changes. |
| Docker and Compose | Start with official runtime assumptions and apply Radar control-plane and Worker restrictions. |

Existing dirty Radar files are part of the integration baseline. They are
applied intentionally after official merge conflicts have been resolved. No
existing Radar file is discarded as a merge shortcut.

### Control Plane and Console

The control plane serves the Sub2API API and the embedded Vue console. Radar
uses the established administrative route family and the main database.

```text
Sub2API admin SPA
  -> embedded Radar and model-health views
  -> authenticated administrative API
  -> Radar services and repositories
  -> PostgreSQL evidence, run, score, aggregate, and alert records
```

Radar menu selection stays within the SPA. It does not open a standalone
Radar URL.

### Worker Contract

`radar-runner`, `radar-grader`, and `radar-statistics` remain restricted
containers addressed by content digest. These settings remain stable:

- Dedicated Worker token and identity.
- `RADAR_LIFECYCLE_PROTOCOL_VERSION=2`.
- Internal-only Worker network and read-only filesystem settings.
- Capability declarations, route profile version, and state volumes.

A candidate rejects a Worker whose registration token, identity, or protocol
version disagrees with the control-plane record. Such a failure blocks
promotion.

## Migration Contract

The migration runner sorts SQL files lexically, stores the complete filename
as the `schema_migrations` primary key, and verifies each applied file's
SHA256 checksum.

1. Preserve every applied Radar migration filename and byte content.
2. Include official `v0.1.171` migrations, including its `190` through `193`
   files.
3. Keep Radar migrations sharing numeric prefixes. Full filenames provide
   independent migration identities.
4. Add a regression test containing official and Radar migrations with the
   same numeric prefix. It verifies both rows and a clean second invocation.
5. Rehearse the complete merged migration set against a disposable PostgreSQL
   database restored from a verified production backup.

A checksum mismatch, missing historical filename, or incomplete schema blocks
the candidate.

## Runtime and Image Contract

The control-plane build follows official `v0.1.171` Dockerfile dependency
versions and lockfile rules, then applies the Radar control-plane overlay.

```text
sub2api/radar-control-plane:0.1.171-radar-v11-YYYYMMDDTHHMMSSZ
```

Promotion uses the resulting immutable image digest. The existing v10 image
digest remains the immediate rollback asset. The 2 GB offshore host receives
a verified image and does not build the candidate.

## Security and Authentication

The release preserves the current Turnstile configuration and does not switch
CAPTCHA providers. Browser verification runs at `sub2api-staging.weihub.cloud`.
That hostname must be added to the provider's permitted hostnames and receive
the same TLS and proxy policy as production before trial execution.

A valid CAPTCHA token must complete the staging login flow. A failed
verification blocks promotion. Release validation uses a dedicated operator
account and keeps credentials out of logs, environment dumps, artifacts, and
reports.

## Verification

### Source Tests

The candidate passes:

- New migration coexistence and checksum regression tests.
- Radar handler, service, repository, route, and Worker protocol tests.
- Radar router, sidebar, embedded view, and model-health frontend tests.
- Official tests for CAPTCHA configuration, Codex outbound identity, billing
  records, refund API contracts, and session refresh.
- Full backend build with generated wiring and embedded frontend.

### Disposable Database Rehearsal

Restore a verified production backup to a fresh disposable database. Record
the backup checksum, candidate image digest, migration list before and after
application, and `schema_migrations` query results.

The rehearsal proves that historical Radar checksums match, missing official
migrations apply exactly once, a second invocation produces no new rows, and
the retained v10 control plane starts against the forward-migrated schema.

### Offshore Isolated Trial

Create a separate Compose project, PostgreSQL volume, Redis volume, Worker
state volumes, internal network, and local port. The trial never shares
production database or Redis storage.

The trial must show:

- Healthy control plane and all three Workers.
- Stable restart counts during a 30-minute observation interval.
- Correct Worker registration and lease acquisition.
- One low-quota evaluation run reaching execution, grading, aggregation, and
  a visible model-health snapshot.
- Embedded Radar and model-health views displaying the trial result through
  normal SPA routes.
- CAPTCHA-protected staging login with a valid token.
- No migration checksum mismatch, Worker authentication failure, Radar HTTP
  5xx, or persistent outbox backlog.

The evaluation uses one test case with `max_tokens=128` and a dedicated
low-quota API key. No load, chaos, or bulk benchmark exercise uses production
traffic in this release.

## Promotion and Rollback

1. Record candidate source commit, clean upgrade-branch status, test reports,
   control-plane digest, and Worker digest.
2. Preserve current control-plane and Worker image digests.
3. Create a production database backup and verify its checksum.
4. Capture configuration hashes, container health, restart counts, and disk
   capacity.
5. Deploy the control plane by immutable digest.
6. Confirm migrations, health, Worker heartbeat, Radar task flow, and
   authenticated console access.
7. Observe the candidate without a restart increase or Radar error markers.

Rollback restores the v10 control-plane and Worker digests. The disposable
rehearsal proves v10 startup against the forward-migrated schema. Automatic
database restoration does not run as part of an image rollback.

## Acceptance Evidence

Acceptance requires all of the following:

- Official tag and merged source commit.
- Original checksums for existing Radar migrations.
- Same-prefix migration coexistence in a disposable rehearsal.
- Passing backend, Worker, and frontend tests.
- Recorded candidate control-plane and Worker image digests.
- Passing offshore Radar lifecycle and CAPTCHA login trial.
- Production backup, pre-promotion state, promotion smoke output, and
  rollback verification.
- HTTP 410 retained for `radar.weihub.cloud`.

# Sub2API v0.1.171 Radar Private GHCR Release Closure Design

**Status:** User-approved design

**Date:** 2026-08-07

## Purpose

This design closes the remaining release gaps for the Sub2API v0.1.171
Radar upgrade. It refines the approved
`2026-08-06-sub2api-v0.1.171-radar-upgrade-design.md` with a private GHCR
distribution contract, the observed offshore topology, isolated trial
requirements, and separate control-plane and Worker rollback evidence.

The release source is fixed at commit
`3fff72a51c53beb94155290bcb13a1a590cfc44e`. Any release-hardening source
change creates a new source commit and requires both candidate images to be
rebuilt from that new commit.

## Chosen Distribution Model

Publish two private `linux/amd64` OCI images:

```text
ghcr.io/a895411690/sub2api-radar-control-plane
ghcr.io/a895411690/sub2api-radar-worker
```

Local release automation receives GitHub `write:packages` access. The
offshore host receives a separate `read:packages` credential. The offshore
credential is entered interactively and stored only in Docker's root-owned
credential file. Release scripts, Compose environment files, evidence, and
logs must not contain either credential.

Each image record contains:

- final source commit;
- release version;
- UTC build timestamp;
- OCI manifest digest;
- image config digest;
- target platform;
- binary or Worker version output.

Deployment inputs use complete `ghcr.io/...@sha256:...` references. Tags are
discovery aids and cannot be used as accepted deployment inputs.

## Build Contract

The control plane builds with
`deploy/Dockerfile.radar-control-staging`. The build command must select that
Dockerfile explicitly, set `linux/amd64`, inject the source commit and release
version, and push directly through Buildx.

The Worker build uses `radar-worker/Dockerfile`. Its base image and Python
dependencies must resolve to fixed release inputs. Version ranges and mutable
base tags are rejected by release tests.

Both images are built after all release-hardening commits are complete. A
source change, Dockerfile change, lockfile change, or release Compose change
invalidates earlier candidate digests.

## Compose and Topology Contract

The established split production topology remains in place:

```text
sub2api project
  control plane, PostgreSQL, Redis

sub2api-radar project
  MinIO, ClamAV, runner, grader, statistics
```

The generic upstream Compose file may retain its upstream default image. The
combined production configuration must resolve the control plane and Workers
to the accepted digest references after all override files are applied.

Trial and rehearsal configurations parameterize all project names, network
names, container names, and volume names. The accepted offshore trial uses:

```text
RADAR_COMPOSE_PROJECT_NAME=sub2api-radar-v11-trial
RADAR_COMPOSE_RESOURCE_PREFIX=sub2api-radar-v11-trial
RADAR_IMAGE_PULL_POLICY=always
```

The reliability overlay cannot replace these names with a shared staging
constant. Candidate startup uses `--no-build` and exact control-plane and
Worker digest references.

## Release Manifest Contract

Promotion and rollback records model two independently versioned artifacts:

| Artifact | Candidate input | Rollback input |
| --- | --- | --- |
| Control plane | GHCR digest reference and digest | retained v10 reference and digest |
| Worker | GHCR digest reference and digest | retained v10 reference and digest |

Manifest validation rejects a missing digest, malformed digest, image and
digest mismatch, identical candidate and rollback digest, mutable tag, or
missing local rollback image. Promotion audits inspect the fully rendered
Compose configuration for both production projects.

## Disposable Migration Rehearsal

Create a fresh custom-format backup of the production PostgreSQL database
outside `/opt/sub2api`. Record its SHA256 without exposing database content or
credentials. Restore it into a new disposable PostgreSQL volume.

The rehearsal must prove:

1. migration 208 and every earlier migration apply exactly once;
2. a second candidate start is idempotent;
3. the candidate control plane becomes healthy;
4. the retained v10 control plane becomes healthy against the forward schema;
5. the retained v10 Worker image remains available and starts with the
   expected protocol configuration.

Rehearsal resources use a dedicated project and are removed only after their
redacted evidence has been captured.

## Offshore Trial

The offshore trial runs beside the existing production projects. It has a
separate PostgreSQL database, Redis instance, object store, ClamAV state,
Worker state volumes, networks, ports, and hostname. It cannot read or write
production application storage.

The trial gate requires:

- healthy control plane, runner, grader, and statistics Worker;
- Worker lifecycle protocol version 2 and fresh heartbeats;
- no restart-count increase during the observation window;
- no Radar HTTP 5xx response;
- no persistent outbox backlog;
- one completed low-quota evaluation;
- visible Radar and Model Health data through embedded console routes;
- successful Turnstile-protected login on the trial hostname.

A failed gate stops the release and leaves both production Compose projects
unchanged.

## Production Promotion

Promotion requires the accepted source commit, two accepted candidate
digests, two verified rollback digests, passing source tests, passing
disposable rehearsal, passing offshore trial, a fresh production backup, and
explicit production authorization.

Promotion updates only the established control-plane and Worker image
references. It renders and audits the final Compose configuration before
running `docker compose up -d --no-build`. Smoke checks cover health,
migrations, Worker heartbeats, one Radar lifecycle, embedded console access,
Model Health data, and Turnstile login. An observation interval follows the
smoke checks.

## Rollback and Failure Handling

An image, health, migration, authentication, lifecycle, or observation gate
failure blocks further promotion steps. If production has already changed,
rollback restores the recorded control-plane and Worker digest references and
repeats smoke checks.

Image rollback does not restore the database. Database restoration is a
separate recovery action requiring explicit authorization. Forward-schema
compatibility is therefore a hard rehearsal gate.

## Verification Scope

Release hardening adds focused tests for:

- trial project and resource-name parameterization;
- missing and malformed candidate digest inputs;
- image reference and digest mismatch;
- separate control-plane and Worker promotion inputs;
- separate control-plane and Worker rollback inputs;
- correct control-plane Dockerfile selection;
- fixed Worker base image and Python dependency inputs;
- fully rendered production image references;
- rollback image availability for both artifacts.

The full existing backend unit, backend integration, frontend, Worker,
Compose configuration, migration rehearsal, lint, and GitHub CI suites remain
required.

## Evidence and Secret Handling

Evidence records commands, timestamps, source commits, image metadata,
configuration hashes, migration lists, health states, restart counts, smoke
results, and release decisions. It excludes environment values, API keys,
registry credentials, database contents, backup contents, session cookies,
and Turnstile secrets.

## Exclusions

This closure does not add benchmark suites, alter Radar scoring policy,
change Worker protocol semantics, combine the two production Compose
projects, re-enable the standalone Radar domain, or perform automatic
database restoration.
